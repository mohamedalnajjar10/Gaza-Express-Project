# Production release gates

## What to prepare on the target environment

1. Create a staging host and a separate production host or account. Set HTTPS for the API and frontend. Restrict direct access to MySQL, Redis and NestJS. The Docker Compose gateway is bound to loopback and is suitable behind a trusted TLS proxy. Verify forwarded-IP settings against the real proxy chain.
2. Provision a runtime MySQL user and a separate migration user for each database. Provide runtime secrets through the platform secret store. The local Compose database account is shared by its API and migrator, so configure separate credentials for a live deployment. Start from `apps/api/.env.production.example`. Keep production secrets distinct from local and staging secrets. In `NODE_ENV=production`, `CORS_ORIGIN` (valid `http`/`https` origin list) and strong 64+ character `JWT_SECRET`, `JWT_REFRESH_SECRET`, and `DELIVERY_CODE_SECRET` are enforced at boot; Swagger UI and `debug`/`verbose` logs are automatically disabled. Set `PLATFORM_BANK_TRANSFER_PHONE` (`^0(?:59|56)\d{7}$`) and verify fee/commission bounds (`PLATFORM_COMMISSION_BPS` / `PRO_COMMISSION_DISCOUNT_BPS` `0..5000`, `DELIVERY_PLATFORM_CUT_BPS` `0..10000`).
3. Provide an image registry and deployment identity scoped to staging. Run the CI workflow on a pushed branch and capture the passing build (including Trivy `container-scan` for fixable HIGH/CRITICAL CVEs). Publish and deploy the tested API and migrator images by digest. Production promotion should require the exact tested image digest and a deployment approval.
4. Configure a supported real SMS provider and verify a code arrives on an authorized test number. Configure WhatsApp Business and independently validate a posted bank transfer in the bank account. Confirm how much cash the driver hands over, the payout rules and the refund policy with operations. Connect an electronic provider only after the merchant account, supported currencies and settlement arrangements are confirmed.

## Gate a release

- From the repository root, run `node infra/verify-release.mjs https://your-staging-host`. This checks HTTPS with normal certificate validation, the built login entry, and all three API health routes through the public gateway. Use the browser journey and authorized provider tests below to verify login, delivery and settlement.
- Take a consistent encrypted database backup and record the restore point. Restore it into a separate database and verify critical row counts, an order and its payment ledger, and the new application reads. Record restore time and data loss against the required RTO and RPO.
- Run the migrator once with migration credentials. Deploy API and worker images. Check `/api/v1/health` and `/api/v1/ready`, then exercise signup, login, checkout, confirmation, delivery and settlement with test identities. Keep the previous image available. Check migration compatibility before any image rollback.
- Run a deployment rehearsal on staging, including a dependency interruption. A readiness failure returns HTTP 503 and liveness remains independent. HAProxy in Compose actively checks database routing readiness. Configure the target load balancer to apply the same routing policy.
- Collect latency, errors, MySQL saturation, Redis memory, queue age and failed or uncertain SMS deliveries. Set ownership for alerts. Run the load profiles with production-like data and request mix. Record p95/p99, throughput and failure rates. The local run in `PERFORMANCE.md` is the baseline.

## Google frontend integration

`GOOGLE_AUTH_ENABLED` defaults to disabled. Keep it disabled until browser testing is complete. Register the exact callback URL with Google and configure frontend and API on the same site over HTTPS in production. The callback verifies state and redirects to `/auth/success` without an access token in the URL. The success page must send `POST /api/v1/auth/google/exchange` to the API with `credentials: 'include'` from the configured frontend origin. The handoff expires after 60 seconds and is consumed once. Existing local accounts with the same email must sign in using their existing method. Account linking requires a separate authenticated flow.

## Store operations

A store owner creates a pending store. An admin lists pending stores at `GET /api/v1/stores/moderation` and sends `PATCH /api/v1/stores/:id/moderation` with `expectedStatus`, `status` and a `reason`. The application records the actor and transition in the same transaction and invalidates the catalog cache. When a store has moderation history, archive it via status instead of hard-deleting it.


## Before deploying the backend remediation

- Take and restore a database backup in staging. Inspect assigned and in-transit orders for duplicate driver assignments before applying the driver reservation backfill. Resolve each conflicting assignment through operations.
- Pause order writes and stop old API and worker replicas before applying the sales projection and OTP migrations. Deploy the new API and web client together for the updated registration, stock availability and store availability contracts. The OTP migration retires old codes and removes their queued secret payloads. Users can request a new code immediately, subject to the usual endpoint rate limits. Production SMS needs an independent `OTP_SIGNING_SECRET`.
- Inject a non-DDL runtime account, an independent migrator account and an account for the worker. Compose reads `COMPOSE_RUNTIME_DATABASE_URL`, `COMPOSE_MIGRATION_DATABASE_URL` and `COMPOSE_WORKER_DATABASE_URL` on the host and passes each service only its own `DATABASE_URL`. Use a TLS-enabled Redis ACL with a separate cache and rate-limit store in production via `COMPOSE_RATE_REDIS_URL` and `COMPOSE_CATALOG_CACHE_URL`. Keep the Compose defaults for local use.
- Route traffic using `/api/v1/routing-ready`. The full `/api/v1/ready` probe also checks the rate-limit store. Keep authentication, writes and webhooks unavailable while its shared limits are down. Catalog reads have a bounded per-process fallback.
- Schedule `npm run maintenance:prune` on a protected runner with database credentials (or use the `maintenance` Compose profile via `infra/crontab.example`), and schedule `infra/backup.sh` with `BACKUP_PASSPHRASE` set to produce encrypted MySQL and MinIO `product-media` backups (`infra/crontab.example`). Start with one daily execution and monitor the per-batch counts. Defaults retain expired OTPs for 7 days, expired refresh sessions and resolved SMS records for 30 days, and read notifications for 180 days. Unresolved SMS and unread notifications remain available. Check these periods against the deployment's retention policy before scheduling.
- Ensure any external TLS reverse proxy in front of Nginx/HAProxy keeps `proxy_read_timeout` >= `150s` and disables buffering on `/api/v1/orders/updates` so the 120s SSE stream lease and 15s heartbeats are not prematurely closed.
- In SMS operations, inspect queue age and the Twilio message records for uncertain deliveries. After obtaining evidence, an admin can record a final result with `PATCH /api/v1/notifications/sms-queue/:id/resolution`. Verify SMS tracking and the acknowledged refund/return workflows during staging rehearsal.
- Compose serves the versioned API at `/api/v1`. Rebuild the web image after changing `SMS_PROVIDER`. The Compose build hides phone registration and verification while SMS is disabled. When Twilio is enabled, start the `sms` profile and verify delivery to a staging test identity.
