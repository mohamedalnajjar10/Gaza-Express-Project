# Payments and delivery

The API uses ILS and stores exact decimal amounts. Set `PLATFORM_COMMISSION_BPS` (`0..5000`), `PRO_COMMISSION_DISCOUNT_BPS` (`0..5000`), `DELIVERY_BASE_FEE_ILS` (non-negative 2-decimal), `DELIVERY_PER_KM_FEE_ILS` (non-negative 2-decimal), `DELIVERY_PLATFORM_CUT_BPS` (`0..10000`), `DRIVER_FEE_ILS` (non-negative 2-decimal), and `PLATFORM_BANK_TRANSFER_PHONE` (`^0(?:59|56)\d{7}$`, default `0592229436`) before accepting orders with live payout terms. Defaults are zero for fees/commissions. Commission resolves in priority order: store override (`Store.commissionBps`, managed by admins via `PATCH /stores/:id/monetization`), category default (`StoreCategory.defaultCommissionBps`, managed by admins via `PATCH /store-categories/:id`), then `PLATFORM_COMMISSION_BPS` (with `PRO_COMMISSION_DISCOUNT_BPS` subtracted for `PRO` plan stores without a custom override).

Commission applies to `itemsSubtotal` (`amount - deliveryFee`). When `deliveryFee > 0`, `DELIVERY_PLATFORM_CUT_BPS` determines the platform's delivery margin (`platformShare = orderCommission + deliveryMargin + companyFeeApplied`) and the remainder goes to `driverShare`; when `deliveryFee` is zero (free delivery threshold met or legacy zero-fee config), `DRIVER_FEE_ILS` is used instead. `DeliveryCompany.feePerOrder` (`PATCH /delivery-companies/:id`) adds per-order company platform fees so `storeShare + driverShare + platformShare = amount`. All share rates and amounts are snapshotted onto `Payment` at order acceptance and must fit within `finalTotal`.

- Choose `paymentMethod` on checkout. `CASH` is the default (earns 10 reward points on delivery). `BANK_TRANSFER` uses a private receipt and beneficiary statement review (earns 20 reward points on delivery). `ELECTRONIC` is limited to the local signed sandbox and is disabled in production.
- `GET /finance/merchant-summary` gives store owners per-store plans, effective commission rates, delivered sales, `config.platformBankPhone`, and pending settlements; `GET /finance/platform-summary` gives admins platform-wide GMV, shares, category commissions, store tiers, `config.platformBankPhone`, and `pendingSettlementOrdersList` (up to 25 unsettled delivered orders).
- Admin approves a verified driver with `PATCH /drivers/:id/approval`. The driver uses `PATCH /drivers/me/availability`. The admin offers a ready order through `assign`. The driver uses `accept_assignment` or `decline_assignment` before the five-minute offer expires. An accepted active delivery reserves the driver through a unique MySQL constraint.
- The assigned driver records `pick_up`. The customer reads `GET /orders/:id/delivery-code` and shares the six-digit code on arrival. For `deliver`, send `deliveryCode` and for cash send `collectedAmount`. A successful delivery atomically consumes the code and posts the collection and shares. Wrong codes are limited to five attempts. `report_delivery_issue` records a reason. An admin can use `reset_delivery_code` with a reason to allow a fresh code, including for pre-migration orders already in transit. This action still requires the customer's code to complete delivery. When the store has confirmed physical return of an undeliverable order, an admin sends `confirm_return` with the current order version and a reason. The order becomes cancelled, the driver is released, and payment follows the cancellation rules.
- `GET /orders/:id/payment` shows payment to the customer and the associated ledger to admins. Admins record actual full cash handover or completed payouts using `POST /orders/:id/settlements` and `{ kind, reference }`. For cash orders handover must precede payouts. The endpoint records a completed external action and does not move money on its own. Reusing the same reference is safe.

## Local bank transfer

1. Checkout offers Bank of Palestine. The default platform recipient comes from `PLATFORM_BANK_TRANSFER_PHONE` (default `0592229436`). Owners can override it in store settings (`bankTransferPhone`, 10 digits starting with `059` or `056`). Verify the beneficiary and enable transfers with the bank before live use. A payment snapshots the recipient when the final amount is approved. Previously issued payments retain their legacy transfer instructions.
2. The customer attaches one JPEG, PNG or WebP receipt (up to 5 MiB), and may also supply `transferReference`, `senderPhone`, and `claimedAmount` (which must match the order total when provided). Before re-encoding to WebP and storing the private copy in MySQL, the API runs deterministic forensic checks: SHA-256 exact duplicate detection and 64-bit dHash near-duplicate detection across orders, transfer reference uniqueness, image editing-software metadata scanning (`Photoshop`, `Canva`, `GIMP`, `Photopea`, etc.), and resolution/visual entropy checks. Access requires the order customer, its store owner or an admin. Upload returns the submission status and risk level. Store reviewers see check labels and outcomes. Cross-order references and detailed forensic evidence are reserved for admins. WhatsApp acknowledgements remain informational.
3. Verify the posted credit, currency, amount and unique reference in the beneficiary bank statement before reconciliation (`POST /orders/:id/payment/bank-reconciliation`). Automated receipt checks assist reviewers and never auto-confirm payment as `PAID` without statement verification. The platform admin confirms transfers to the platform (`PLATFORM_BANK_TRANSFER_PHONE`). For a store recipient, its owner can also reconcile. Store-collected gross funds must be remitted to the platform and recorded before payouts. Both store owners (for their stores) and admins (including on platform-collected receipts) can report a suspected forged or unpaid receipt (`POST /orders/:id/payment/receipt/report`) with a reason. An admin reviews reported or `FLAGGED_SUSPICIOUS` receipts via `/api/v1/finance/receipt-reports` and `POST /orders/:id/payment/receipt/review`, either dismissing (`decision: 'dismiss'`) to allow reconciliation or confirming fraud (`decision: 'suspend'`) to suspend the customer (`is_active = false`), increment `sessionVersion`, and revoke refresh tokens. An open/confirmed fraud report or unreviewed `FLAGGED_SUSPICIOUS` receipt blocks reconciliation (`409`).
4. A bank or sandbox payment confirmed after cancellation goes to `REFUND_REQUIRED`. This signals operations to return the funds. After returning the funds via the actual payment channel, an admin submits the exact amount, currency and unique reference to `POST /orders/:id/payment/refund`. This records the reversal and changes the payment to `REFUNDED`. Repeating the same reference on the same order returns the existing result.

The sandbox confirms payment using a signed POST to `/api/v1/webhooks/payment-sandbox/:id`. Set `PAYMENT_SANDBOX_SECRET` in a non-production environment. Compute `sha256=` plus the HMAC-SHA256 of `<id>.<raw request body>` and send `x-sandbox-signature`. The body contains `amount`, `currency`, and `reference`. Use a distinct secret and test data. A commercial provider and bank API can be attached once their contracts and credentials are available.
